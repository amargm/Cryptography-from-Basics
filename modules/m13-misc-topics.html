Connected Topics: X.509 Anatomy, Formats & Cryptographic Serialization

Deconstructing the operational glue of applied public-key cryptography: the X.509 certificate standard, certificate packaging formats, canonical serialization, and cryptographic timestamping.

1. Deep Dive: Anatomy of an X.509 Certificate (RFC 5280)

In Module 09 we introduced Public Key Infrastructure (PKI) conceptually. But in production systems, engineers do not pass around abstract "keys" — they pass around X.509 v3 Certificates.

An X.509 certificate is an internationally standardized, cryptographically signed data structure defined in RFC 5280 that securely binds an entity's identity (such as a domain name, email address, or organization) to a public key.

The Three Top-Level Fields of Every X.509 Certificate

1. TBSCertificate (To-Be-Signed Certificate):
The payload containing all actual certificate metadata, identity details, validity dates, subject public key info, and RFC 5280 extensions.
2. SignatureAlgorithm:
The exact cryptographic algorithm identifier (OID) used by the Certificate Authority to sign the certificate (e.g., sha256WithRSAEncryption, ecdsa-with-SHA256, or ed25519).
3. SignatureValue:
The raw digital signature bytes produced by the CA's private key signing the DER-encoded TBSCertificate.

Detailed Dissection of TBSCertificate Internals

The TBSCertificate block contains the actual operational data verified by TLS clients during handshakes:

Field Name Purpose & Standards Real-World Security Implication
Version Identifies X.509 version (v1 = 0, v2 = 1, v3 = 2). Modern certificates are virtually always v3 (value 2). Version 3 enabled Extensions (SAN, Key Usage, Constraints). Never trust v1 certificates on modern networks.
SerialNumber Unique positive integer assigned by the CA up to 20 octets (160 bits). Must contain at least 64 bits of cryptographically strong entropy (CAB Forum baseline) to neutralize hash collision attacks (such as the Flame malware MD5 collision).
Signature Algorithm identifier for the CA signature (must match top-level SignatureAlgorithm). Prevents algorithm substitution attacks against the certificate payload.
Issuer Distinguished Name (DN) of the CA that verified and signed this certificate. Clients use this to match against their trusted Local Trust Store (e.g., DigiCert Global Root G2, Let's Encrypt ISRG Root X1).
Validity Two timestamps: notBefore and notAfter. Since Sept 2020, major browsers mandate maximum 398-day TLS certificate lifetimes. Certificates valid for longer are outright rejected.
Subject Distinguished Name (DN) of the entity owning the public key (Country, Org, Common Name). Legacy note: The Common Name (CN) field was deprecated by RFC 6125. All modern browsers require SAN!
SubjectPublicKeyInfo The algorithm identifier (e.g., RSA, EC P-256, Ed25519) plus the raw public key bitstream. The public key the TLS client will use during key exchange and handshake authentication.
Extensions (v3) Critical and non-critical policy extensions defined in RFC 5280. Enforces domain matching (SAN), certificate authority delegation powers (Basic Constraints), and allowed usages (Key Usage).

Critical X.509 v3 Extensions Every Engineer Must Know

Extensions can be flagged as CRITICAL or NON-CRITICAL. If a TLS client encounters a CRITICAL extension that it does not recognize or understand, RFC 5280 mandates that it MUST immediately reject the certificate!

Subject Alternative Name (SAN)

Lists all valid domain names (DNS:example.com, DNS:*.example.com) or IP addresses (IP:192.168.1.1). Browsers completely ignore the legacy Subject Common Name (CN) if SAN is present or absent!

Basic Constraints (cA: TRUE / FALSE)

Specifies whether this certificate belongs to a Certificate Authority allowed to sign other certificates. For a regular website, cA: FALSE. If an attacker tricks a CA into issuing cA: TRUE, they could forge certs for any domain on Earth!

Key Usage & Extended Key Usage (EKU)

Restricts what the key can do: digitalSignature, keyEncipherment, serverAuth (TLS Web Server), clientAuth (mTLS client), or codeSigning. A serverAuth cert cannot be used to sign executables!

Authority Key Identifier (AKID) & SKID

SHA-1 / SHA-256 hashes of public keys that allow TLS libraries to unambiguously reconstruct the certificate trust chain from leaf -> intermediate -> root without confusion.

2. Certificate Packaging Formats: PEM, DER, PKCS#12 & PKCS#7

One of the most frequent sources of production deployment bugs is format confusion. Certificates and keys are packaged in four primary formats:

Format Common Extensions Binary or Text Contains Private Key? Primary Operating Environment
PEM (Privacy-Enhanced Mail) .pem, .crt, .cer, .key ASCII (Base64 armored) Yes (optional, in separate file or block) Linux, Nginx, Apache, OpenSSL, Cloud Providers (AWS/GCP/Azure).
DER (Distinguished Encoding Rules) .der, .cer Raw Binary Rare (primarily stores single certs/keys) Java KeyStore imports, Windows binary certificates, Hardware tokens.
PKCS#12 (PFX) .p12, .pfx Encrypted Binary Archive Yes (Password Protected) Microsoft Windows Server (IIS), Java (default since Java 9), macOS Keychain.
PKCS#7 (CMS) .p7b, .p7c ASCII or Binary NEVER (Certificates and Chains only) Windows certificate chain distribution, S/MIME email signatures.
Engineering Insight: The Anatomy of a PEM File

PEM is literally just DER-encoded binary data passed through Base64 encoding, split into 64-character lines, and enclosed between human-readable header and footer delimiters:

-----BEGIN CERTIFICATE----- MIIFazCCA1OgAwIBAgIRAIIQz7DSQONZRGPgu2OcIwAwDQYJKoZIhvcNAQELBQAw TzELMAkGA1UEBhMCVVMxKTAnBgNVBAoTIEludGVybmV0IFNlY3VyaXR5IFJlc2Vh cmNoIEdyb3VwMRUwEwYDVQQDEwxJU1JHIFJvb3QgWDEwHhcNMjQwMzEzMDAwMDAw ... (Base64 Encoded ASN.1 DER Payload) ... -----END CERTIFICATE-----

Because PEM is standard text, multiple certificates can be concatenated into a single file to create a full chain bundle (Leaf cert first, followed by Intermediate CA certs).

3. Cryptographic Serialization & Canonical Encodings (ASN.1 DER vs CBOR vs JCS)

In cryptographic engineering, you cannot digitally sign or hash an abstract data structure. You can only sign and hash an exact sequence of bytes.

The Fatal Non-Deterministic Serialization Bug:

Suppose Alice creates: {"amount": 100, "recipient": "Bob"}.
Alice hashes those exact bytes with SHA-256 and signs the hash with her private key.
The message is sent over the network. A JSON parser deserializes and re-serializes the payload as:
{"recipient": "Bob", "amount": 100} (key order flipped!) or adds a space: {"amount": 100}.

The Result: The SHA-256 hash completely changes due to the Avalanche Effect! Bob verifies Alice's signature against the new hash, and the signature FAILS, even though the semantic meaning was identical!

How Cryptography Solves This: Canonical Encodings

To ensure digital signatures never fail due to formatting differences, cryptographic protocols mandate canonical encoding rules where every data structure has exactly ONE unambiguous byte representation:

Canonical Standard How It Eliminates Ambiguity Primary Real-World Ecosystem
ASN.1 DER (Distinguished Encoding Rules) Strict Tag-Length-Value (TLV) encoding. Boolean TRUE must be 0xFF. Lengths must use the minimum number of bytes. Set elements must be sorted lexicographically. X.509 Certificates, PKI, SSH Keys, TLS Handshakes.
CBOR (RFC 8949) / COSE Concise Binary Object Representation. Enforces strict map key sorting and canonical integer representations without floating-point ambiguities. FIDO2 Passkeys, WebAuthn, IoT Constrained Devices.
JCS (JSON Canonicalization Scheme, RFC 8785) Rules for sorting JSON keys alphabetically and normalizing Unicode, whitespace, and floating-point scientific notation before hashing. Decentralized Identifiers (DIDs), Verifiable Credentials.

4. Cryptographic Time: NTP Vulnerabilities, NTS & RFC 3161 TSP

Nearly all cryptographic security guarantees are bounded by time:

  • Certificates have strict NotBefore and NotAfter validity windows.
  • OAuth 2.0 and JWT tokens have expiration timestamps (exp).
  • Kerberos authentication tickets and TOTP codes (authenticator apps) reject timestamps outside a 30-second window to prevent replay attacks.

If an adversary on a local network can manipulate a server's time using spoofed Network Time Protocol (NTP) packets, they can trick a server into accepting an expired, compromised TLS certificate or invalidating active session tokens.

Network Time Security (NTS, RFC 8915) Network Defense

Standard NTP transmits timestamps in unauthenticated UDP packets. Network Time Security (NTS) provides cryptographic security for time synchronization:

1. Client connects via TLS 1.3 to authenticate the time server.
2. Both derive AEAD session keys and cookies.
3. Time queries are authenticated with an AEAD tag in hardware, preventing MitM time shifts!
Timestamp Authorities (RFC 3161 TSP) Legal Proof

Suppose Alice signs a contract with a digital certificate that expires in 2026. In 2028, a dispute arises. Did Alice sign before the certificate expired?

Alice sends the document hash to a certified Timestamp Authority (TSA). The TSA appends the current atomic clock time and digitally signs the package. This legally proves the signature existed before expiration or revocation!
