Applied Real-World Systems: TLS, E2EE & Passkeys

Now we watch all individual primitives—symmetric AES, Elliptic Curve Diffie-Hellman, SHA-256 hashes, digital signatures, PKI, and Base64—assemble into the real-world applications that secure civilization.

1. Process Walkthrough: The TLS 1.3 Handshake

Every time you see the green padlock in your browser, your device and the remote web server execute a 1-Round-Trip-Time (1-RTT) handshake in under 60 milliseconds.

In 2018, TLS 1.3 (RFC 8446) completely overhauled web security, removing all legacy ciphers (RSA key exchange, CBC mode, and SHA-1 were banned) and enforcing Perfect Forward Secrecy.

2. End-to-End Encryption (E2EE) & The Double Ratchet

In standard HTTPS, your connection is encrypted between your phone and the server (e.g., Slack or Instagram). But the server itself holds the decryption key and can read every message.

In End-to-End Encryption (E2EE) (Signal, WhatsApp), the servers act strictly as blind relays. Messages are encrypted on Alice's device directly to Bob's public key.

Visual Architecture: In-Transit (HTTPS) vs. True End-to-End Encryption (E2EE)
️
In-Transit Encryption (Standard HTTPS)
e.g. Slack, Standard Email, Instagram
Data is encrypted on the wire between client and cloud. However, the cloud server decrypts every message into memory and stores it in databases.
Server Visibility: Full Plaintext Readable
Vulnerable To: Subpoenas / Insider Threats / Server Hacks
️
End-to-End Encryption (True E2EE)
e.g. Signal, WhatsApp, iMessage
Data is encrypted on Alice's device with Bob's private device key. Cloud servers act as blind routers passing opaque ciphertext.
Server Visibility: Zero Knowledge (Blind Relay)
Protection: Immune to Server Breaches
The Double Ratchet Algorithm: Unbreakable Chat

Created by Trevor Perrin and Moxie Marlinspike for Signal, the Double Ratchet Algorithm combines two cryptographic gears:

  1. The Symmetric KDF Chain Ratchet: Every single text message derives a brand-new message key and advances the chain forward. Once a message key is used, it is erased instantly (Forward Secrecy).
  2. The DH Ratchet: Every time Bob replies to Alice, a fresh ephemeral Diffie-Hellman exchange is mixed into the ratchet. This provides Post-Compromise Security (Break-in Recovery): even if a spy clones your phone today, the moment your friend replies tomorrow, the ratchet rolls forward and permanently locks the spy out!

3. Anatomy of Modern Identity: JSON Web Tokens (JWT)

When you log into a modern cloud service or web app, the server doesn't keep a database record of your session; it hands your browser a signed JSON Web Token (JWT).

Notice how a JWT is simply 3 Base64URL-encoded strings separated by dots: Header.Payload.Signature:

Worked Example

Dissecting and Tampering with a JSON Web Token (JWT)

Let's trace how modern web servers verify a user's identity without storing session state in a database:

1
Server Issues Signed Token on Login:
• Header: {"alg":"HS256","typ":"JWT"} → Base64URL: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
• Payload: {"user":"Alice","role":"member"} → Base64URL: eyJ1c2VyIjoiQWxpY2UiLCJyb2xlIjoibWVtYmVyIn0
• Signature: HMAC-SHA256(Header + "." + Payload, SecretKey) → s8E_w7x9...
2
The Privilege Escalation Attempt:
Alice decodes the payload, changes "role":"member" to "role":"admin", re-encodes it into Base64URL, and sends the modified token in an HTTP Authorization header to access administrative settings.
3
Verification at Server:
The server takes the received Header and received Payload, recalculates HMAC-SHA256(Header + "." + Payload, SecretKey). Because Alice modified the payload and does not know SecretKey, the recalculated signature does NOT match the signature on the token.
Response: 401 Unauthorized: Invalid Signature.
️ Lesson: Client-side tokens can be read by anyone, but they cannot be altered by anyone without breaking the cryptographic seal!

4. Passkeys (FIDO2 / WebAuthn): The Death of Passwords

For 50 years, computer security relied on shared secrets (passwords). Passwords suffer from an inescapable human vulnerability: Phishing. If an attacker creates a fake look-alike login page, a human will type their password into the fake site.

Authentication Method How It Operates Phishing Resistance
SMS 2FA Sends a 6-digit text message over cellular networks. WEAK: Vulnerable to SIM-swapping, cellular SS7 interception, and phishing proxies.
TOTP (Authenticator App) Generates a 6-digit code every 30 seconds using HMAC(Key, Time / 30). Moderate: Eliminates SIM swapping, but an attacker using a real-time reverse proxy (like Evilginx) can steal the 6-digit code and log in.
Passkeys (FIDO2 / WebAuthn) The device's Secure Enclave holds an asymmetric private key. The browser binds the domain name (bank.com) into the cryptographic challenge. UNPHISHABLE: Even if you are tricked into visiting bank-fake-login.com, the browser sends the fake domain in the challenge. The enclave will refuse to sign for the wrong domain!
